# Vellum Domain Glossary

This file defines terms used across Vellum's codebase that have specific
meaning in this project. Update as terms are resolved during design
discussions (typically a `grill-with-docs` or `grill-me` session).

Keep entries domain-level, not implementation-level. Cross-reference ADRs
at `docs/adr/` for the *why* behind a term.

---

## Terms

### MCP Server

The server-side surface that exposes Vellum's `tool-registry` as a
Model Context Protocol endpoint at `POST /api/mcp`. Third-party MCP
clients (e.g. Claude Desktop, Cursor) connect to this to call Vellum's
canvas-editing tools over JSON-RPC.

**Primary use case:** users want to edit their Vellum canvas from
inside their preferred AI client without opening the Vellum web app —
e.g. "in Cursor, ask Claude to draw the system architecture into my
vellum canvas". The MCP Server is the "canvas backend" plug that any
MCP-aware AI client can connect to. Vellum's own in-app AI panel
(M14, AiSidePanel) continues to cover the in-browser flow; M15
extends the same capability to external clients.

**Transport:** stateless Streamable HTTP, single endpoint
`POST /api/mcp`. Methods supported in M15 MVP: `initialize`, `ping`,
`tools/list`, `tools/call`. Methods deferred: `resources/*`,
`prompts/*`, `notifications/*`, `sampling/*` — out of scope for the
core "edit canvas from external AI client" goal.

**Motivation:** Vellum is a personal side-project, not a SaaS product.
M15 is intentionally a *craftsmanship-driven* milestone — the owner
wants to build a proper MCP Server end-to-end to deepen familiarity
with the protocol, not because a real third-party integration is
queued. This shapes scope: PAT (not OAuth), opaque token (not JWT),
no token-level scope, no enterprise concerns. If real outside users
ever appear later, OAuth / fine-grained scope / multi-tenant
hardening can layer on top of the same `personal_access_tokens` table
without migration.

Distinct from Vellum's **in-process agent runtime** (apps/api/src/agent/),
which uses the same `tool-registry` directly without MCP serialization.
Both paths feed into the same `applyMutation` + permission-guard layer.

Introduced in: M15 (issue #16, in design as of 2026-05-13).

### MCP Client

Third-party application that connects to **Vellum's MCP Server** over
JSON-RPC. Examples: Claude Desktop, Cursor, Zed.

**Vellum itself is NOT an MCP Client.** Vellum's own agent runtime drives
the same tools directly in-process; if Phase 3+ ever wants Vellum's agent
to call *other* MCP servers (e.g. Notion's), that would be a new role
added then — not part of M15.

### Personal Access Token (PAT)

Opaque random token (format: `vlm_pat_<random>`) generated by a user in
Settings → API Keys. Used by MCP clients to authenticate to Vellum's MCP
Server.

**Storage:** plaintext shown to the user exactly once at creation; DB
stores SHA-256 hash + optional `expires_at`.

**Scope:** bound to a single user. **Not** bound to a specific canvas —
the MCP client passes `canvasId` on each `tools/call` and the server
runs the existing `permission-guard.requireRole()` against that
(user, canvas) pair at request time. Same model as GitHub PAT: one
token across all repos, server checks repo-level permission per call.

User can create multiple tokens (one per MCP client device is the
expected usage). Revoke by DB delete; takes effect on next request.

**Permission scope:** none at token level. The token's effective
capability on a canvas equals the user's canvas role (owner / editor /
viewer), evaluated at request time. Same as GitHub Classic PAT —
fine-grained / per-tool scopes deferred (DB schema reserves a nullable
`scope` column for future use). Read-only access is achieved by sharing
the canvas as `viewer` to a different user whose own token then
naturally read-only — re-using the existing share mechanism rather than
duplicating it in token scope.

**Rate limit:** per-user bucket (key = `mcp:user:<userId>`) shared
across all of that user's tokens, separate rule (`MCP_TOOL_CALL_RULE` =
60 calls / 60 s) from the UI-driven `AGENT_RUN_RULE` (5 / 60 s).
Rationale: MCP is background AI automation and naturally bursts more
than UI clicks; per-user (not per-token) prevents users from
multiplying capacity by creating extra tokens. `tools/list` and
`initialize` are NOT counted — only `tools/call` consumes the bucket.
429 returns `Retry-After` header and `{errorKey:
"agent.error.rateLimited"}`.

**Why not JWT:** JWT's stateless verify advantage doesn't apply to
long-lived PAT usage — revoke needs DB blocklist either way, which
defeats stateless. Same model as GitHub PAT, Stripe API key, AWS access
key.

### Tool Registry

Single source of truth for the agent tool surface
(`apps/api/src/sync/tool-registry.ts`). Currently 11 entries:

- **6 write tools**: `createShape`, `updateShape`, `deleteShape`,
  `groupShapes`, `ungroupShape`, `connectShapes` — all route through
  `applyMutation` for batch-undo and broadcast.
- **5 read tools**: `listShapesInViewport`, `listShapesInSelection`,
  `getShape`, `getCanvasBounds`, `getViewport` — snapshot-derived,
  no mutation.

The MCP Server (M15) exposes the same registry via `tools/list` and
`tools/call`. Both paths share the registry's Zod schemas and tool
descriptions.

**M15 adds a 12th tool: `listCanvases`** — returns the user's
accessible canvas list `[{id, title, role}]` so MCP clients can
discover which canvas to operate on. This is a read tool that ignores
the `canvasId` parameter; it's specific to the MCP entry point because
the in-process agent already knows which canvas it's attached to.
Exposed as a tool (not an MCP resource) — canvas list is dynamic
user-scoped data and MCP client UI support for tools is broader than
for resources at this time.

**M15 also folds in the Cursor AI Badge cross-tab broadcast fix**
(carried over from M14 verification debt): `cursor-ai-badge.ts`
currently writes `TLInstance.meta.aiActive`, a local-only record. To
make the ✨ overlay visible to collaborators (so others see "this user
is running AI" when shapes start appearing), rewrite to use
`TLInstancePresence.meta` via `editor.store.put` +
`InstancePresenceRecordType.createId(userId)`. Only a boolean flag is
broadcast — conversation content stays per-user (private SSE).
`agent-multi-tab-badge.spec.ts`'s `test.skip` is flipped once this
lands.
